Where Atomix replaces a bigger, costlier stack.

  1. SOC teams paying per gigabyte

    Ingest-based pricing punishes the logs you need most. Atomix stores them for a fraction of the disk, on hardware you choose.

  2. MSSPs with many tenants

    One deployment, many organisations, each with its own users, keys, rules and retention.

  3. Regulated and air-gapped networks

    Offline builds, local storage, audit logs and no data leaving the site.

  4. Teams tired of tuning clusters

    No shards, no JVM heaps, no replica maths. One server, one data directory, one backup.

    How these numbers are worked out

    Atomix. Raw logs per day = EPS × event size × 86,400. Stored = raw ÷ compression ratio. Local disk = stored × local days × 1.3, plus 21% of what moved to object storage (the column index stays local so counts and charts stay instant). CPU and RAM come from a table of measured tiers: ingest and compaction cost about 0.1 core per 1,000 EPS of 1 KB events, and the rest is search headroom. RAM is at least one day of stored data for the file cache.

    Elasticsearch. Disk = raw × (local + object days) × index factor × (1 + replicas) × 1.25 for disk watermarks. The days Atomix keeps on local disk go on hot nodes at 1 GB of RAM per hot disk GB; the days it keeps in object storage go on warm nodes at 1 GB per warm disk GB, as Elastic's hot-warm architecture would do. At least 3 nodes. Each node is a 64 GB machine with a 31 GB JVM heap. Elastic's frozen tier with searchable snapshots would lower this further for very long retention, but it needs an Enterprise licence. The Elastic Cloud range multiplies the cluster's RAM by two published Standard-tier rates.

    Prices. List prices, monthly, no commitments or discounts, converted to USD where needed. Each provider gets the smallest plan that meets the CPU and RAM, plus extra disk at the provider's block or network storage rate, plus object storage for the warm tier. Software licences are not included on either side.

        FAQ

        Questions we get asked.

        How does Atomix store logs so small?
        Logs are compressed with CLP, which separates each event's structure from its variable values and stores both in columns. Alongside every archive, Atomix keeps a small column index of the fields people filter and count on. Counts, charts and field filters are answered from that index; only free-text search and document fetches open the archive.
        Is search slower than Elasticsearch?
        Counts, charts and field queries are answered from the column index in milliseconds. Free-text search scans archives and takes a few seconds per 100 million events on an 8-core server. If most of your searches are free text over very long ranges, Elasticsearch's inverted index will be faster; if they are field filters, dashboards and rules, Atomix is usually faster and far cheaper.
        Can I keep a year of logs?
        Yes. A lifecycle policy moves archives older than your local window to S3-compatible storage and keeps the column index local, so dashboards and counts over the whole year stay instant and a search fetches the archive on demand.
        What do alerts do today?
        Rules raise alerts with the matching events, observables and a rule-specific detection view. Analysts acknowledge, assign, tag, add notes and close with a classification. Automated actions come with the SOAR playbook engine, which is in development.
        How do I get logs in?
        Through the JSON ingest API with an API key: anything that can POST JSON (Logstash, Fluent Bit, Vector, a script) works today. Native agents for Windows, Linux and macOS are in development.
        Is the sizing calculator exact?
        It is an estimate from measured numbers on real logs. Your compression ratio depends on your sources; the Elasticsearch figures use the sizing rules Elastic and most operators recommend; prices are list prices that change. Use it to compare orders of magnitude, then verify with the provider.
